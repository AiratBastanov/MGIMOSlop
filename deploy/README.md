# Эксплуатация на Linux

[Локальная установка Windows](../docs/SETUP.md) · [Архитектура](../docs/ARCHITECTURE.md)

Этот раздел сохраняет проверенную ранее схему Linux: Python 3.14.10, PostgreSQL 17.11, Gunicorn 26.2.0 и Caddy 2.11.4. Она выполнялась в локальном Docker/Linux при предыдущей версии продукта. Полная установка текущего комплекта проверена на Windows; новое развёртывание на Linux и внешний сервер не заявляются проверенными. Docker не обязателен для эксплуатации и не устанавливается этой инструкцией.

## Схема узла

Caddy принимает HTTPS и проксирует запросы в Gunicorn на `127.0.0.1:8000`. PostgreSQL и Gunicorn недоступны напрямую извне. Приложение запускается непривилегированным пользователем; его роль БД владеет только своей базой, без административных прав.

Шаблоны: [Caddy](Caddyfile.example), [systemd](deanery.service.example), [Gunicorn](gunicorn.conf.py). Домен, каталоги, firewall, резервное копирование и секреты задаёт оператор. Шаблоны не означают, что сайт уже размещён.

## Установка и статика

Новая БД должна быть пустой. Используйте отдельный каталог приложения, затем:

```sh
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements/production.txt
.venv/bin/python -m pip check
.venv/bin/python scripts/create_local_database.py --database deanery_demo --port 5432
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py prepare_demo --database deanery_demo
```

Последние две команды используют ту же композицию, что [основная установка](../docs/SETUP.md); выполнение нового состава на Linux отдельно не проверялось. Пароли создаются локально и не включаются в исходники. На рабочей БД `prepare_demo` не является шагом обновления или старта.

Собранные assets поставляются вместе с manifest. Для изменения frontend нужны Node 22.20.0 и npm 10.9.3:

```sh
npm --prefix frontend ci
npm --prefix frontend run build -- --configLoader runner
```

Конфигурацию production передайте через защищённое окружение службы или JSON по `DEANERY_CONFIG`. [.env.example](../.env.example) не читается автоматически. Для systemd используйте закрытый `EnvironmentFile`. Для ручных команд нужно отдельно загрузить те же переменные в свой защищённый shell.

Требуются `DJANGO_SETTINGS_MODULE=deanery.settings.production`, случайный сохранённый `DJANGO_SECRET_KEY`, точные `DJANGO_ALLOWED_HOSTS`, HTTPS origins в `DJANGO_CSRF_TRUSTED_ORIGINS`, DB-параметры и `PUBLIC_BASE_URL`. После настройки:

```sh
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/python manage.py check --deploy
.venv/bin/gunicorn -c deploy/gunicorn.conf.py deanery.wsgi:application
```

Caddy раздаёт только `staticfiles`. Исходники, `.local`, дампы, письма и приватные файлы не являются static. Запросы к фото и вложениям идут через Django с проверкой доступа. `runserver --insecure` на внешнем узле не применяется.

## Доверенная цепочка и вход

Только для **одного Caddy на том же узле**, без CDN перед ним, задаётся `DJANGO_CLIENT_IP_TRUSTED_PROXY=127.0.0.1`. Шаблон Caddy перезаписывает `X-Deanery-Client-IP` адресом непосредственного посетителя. Django принимает единственный корректный IP только от доверенного peer. Произвольные `Forwarded` и `X-Forwarded-For` не определяют пользователя ограничения входа. В local/direct режиме forwarded metadata игнорируются.

Другая proxy/CDN-цепочка требует отдельной проверки. Порог Axes — пять неудачных входов для пары логин/IP, ожидание 15 минут; успешный вход сбрасывает счётчик. Не делайте проверки блокировки на демонстрационных аккаунтах организаторов.

Production включает Secure cookies, HTTPS redirect и HSTS 3600 секунд. Предупреждения Django о `includeSubDomains` и `preload` не подавляются: их включение требует контроля домена и отдельного решения оператора.

## Обновление

Сохраните PostgreSQL, конфигурацию и текущую версию исходников. Подготовьте новый каталог кода, установите закреплённые зависимости, примените необходимые **прямые** миграции, соберите/проверьте static, выполните `check --deploy`. Переключите свою службу на новый каталог и проверьте готовность, вход и ранее сохранённую заявку.

Не запускайте первичное заполнение при рестарте. Не заменяйте рабочую БД демодампом. Сохраните прежний Django secret, постоянные DB-параметры и закрытые файлы вне сменяемого каталога релиза. Смена учебных фактов выполняется отдельным просмотренным импортом с ожидаемой текущей ревизией.

## Резервная копия и восстановление

Обычный `pg_dump` включает версии работ, отзывы, заявки, уведомления, JPEG-фото и бинарные вложения. Конфигурация, Django secret и файл демопаролей сохраняются отдельно. Локальные `.eml` при необходимости архивируются отдельно: в БД хранится состояние почтовой очереди, не эти файлы.

Утилиты PostgreSQL **не читают** `DB_*` приложения. Всегда задавайте явные host, port, role и database. Пример с локальным TCP-портом 5432 и закрытым `PGPASSFILE` (права `0600`, каталог `0700`):

```sh
export PGPASSFILE=/srv/deanery/private/pgpass
pg_dump -w -h 127.0.0.1 -p 5432 -U deanery_demo -d deanery_demo -Fc -f /srv/deanery/private/backup.dump
```

Администратор создаёт **новую**, ранее не существовавшую БД и отдельную роль владельца, например `deanery_restore_check`, без административных прав. Пароль вводится интерактивно и добавляется в закрытый PGPASSFILE. Восстановление выполняется под этой ролью:

```sh
pg_restore -w -h 127.0.0.1 -p 5432 -U deanery_restore_check -d deanery_restore_check --no-owner --no-privileges --exit-on-error --single-transaction /srv/deanery/private/backup.dump
```

Не используйте `--clean` и не восстанавливайте поверх working/demo. Проверьте фактические database/user/port, владельцев таблиц и sequences, миграции, учебную историю, заявки, отзывы, прочтения, хеши паролей, сессии и байты файлов. Для `btree_gist` сервер должен иметь установленное trusted-расширение; приложению достаточно CREATE в своей БД. Переключение службы на восстановленную базу — отдельное решение после проверки.

## Почта и внешняя доступность

По умолчанию письма сохраняются локально. Команда `manage.py deliver_notifications --limit 100` обрабатывает сохранённую очередь, повторно проверяя адрес, предпочтения и доступ. Настоящий SMTP требует отдельной конфигурации и разрешения. Сохранённое письмо или SMTP acceptance не доказывает получение адресатом.

Перед внешней демонстрацией отдельно проверяются DNS, доверенный HTTPS, firewall, автозапуск, сохранение данных, резервное копирование и доступ из российской сети без VPN. Публичный хостинг и конкурсная подача не следуют из GitHub-публикации.
